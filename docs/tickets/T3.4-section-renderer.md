# T3.4: Section renderer and blocks

Run Stage 1 first (see `workflow.md`). Write no code until Haider approves.

## Goal

Render a service's `sections` array as page content. Each section is a typed block; the page structure is data, so content tickets later need no component changes.

## Scope

New components in `src/components/service-sections/`, each with a colocated `Component.test.tsx`:

| Component         | Notes                                                                                             |
| ----------------- | ------------------------------------------------------------------------------------------------- |
| `ServiceSections` | `switch` on `section.type` over the `ServiceSection` union, with a `never` exhaustiveness default |
| `ProseSection`    | Text content block                                                                                |
| `FeatureSection`  | Layout variants: `grid`, `alternating`, `list`                                                    |
| `StepsSection`    | Ordered steps                                                                                     |
| `SpecBand`        | Key specs or facts band                                                                           |
| `FaqSection`      | Uses `<details>`, zero JS                                                                         |

Also wire `ServiceSections` into `ServicePageTemplate` if that is not already done. Check first.

## Already decided

- Server Components only. No Client Component in this ticket
- `switch` renderer, not a `Record<type, Component>` registry. TS narrowing and `never` exhaustiveness are the reason
- Components receive typed props and never import data files
- Section data may contain `LucideIcon` references because every block is a Server Component
- No Playwright spec in this ticket. The T3.3 data-driven spec covers routing; sections are content-shaped and out of scope there
- Tests use typed fixture data, never real service data
- Tokens only, literal class strings for variants, no raw hex
- The `h1` comes from `ServiceHero`. Blocks use `h2` and below

## Out of scope

- `VideoSection` and `VideoEmbed` (T3.5)
- Any real page content (T3.6 to T3.9)
- Changing the `ServiceSection` union shape. If it truly must change, say so in Stage 1 and wait for approval
- New dependencies

## Read first

- `src/types/service.ts`: the real `ServiceSection` union. Use its exact field names and variants
- `src/components/service-sections/ServicePageTemplate.tsx` and `ServiceHero.tsx`: layout and spacing already in use
- `src/components/ui/SectionWrapper.tsx` and `src/lib/service-themes.ts`
- `docs/conventions.md`, `docs/design.md`, `docs/testing.md`

## Settle in Stage 1

Suggested starting positions, not decisions:

1. **Semantics:** steps as `<ol>`, spec band as `<dl>`, FAQ as `<details>` with `<summary>`, decorative icons `aria-hidden`
2. **Video member:** if the union already has a `video` type, the `never` default will fail to compile until it is handled. Options: render `null` with a short comment until T3.5, or leave the member out of the union until T3.5. Pick one and say why
3. **Shared wrapper:** whether blocks wrap themselves in `SectionWrapper` or the renderer does it once. Prefer once, in the renderer
4. **FeatureSection images:** whether `alternating` shows images, and whether the union has a field for them. Follow the union; do not invent fields
5. **Visual check:** no service has `sections` data until T3.6, so there is nothing to look at. Options: a temporary fixture route that is removed before commit, or temporary `sections` data on one service that is reverted before commit. Ask Haider which he prefers

## Tests expected

- One test file per block: renders the right element, uses the right semantics, each variant of `FeatureSection`, empty or minimal data does not crash
- `ServiceSections.test.tsx`: one fixture per `type` renders the matching block, order is preserved, an empty array renders nothing
- Assert on role, text and href. Never on CSS classes
