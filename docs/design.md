# Design

## Direction

- Dark theme, single orange accent, Inter only. Hierarchy comes from weight, size and tracking, not a second typeface
- Sporty and minimal. Base backgrounds stay flat, with no alternating light and dark bands. Service-page sections may add three accent motifs only: a large faded section number, a skewed accent stripe, and a soft radial accent glow behind the heading (`bg-radial from-accent/10`). The closing bands add one more: a skewed badge chip. See Service page sections and Closing bands
- Page sections share one divider (`divide-y divide-border` on the wrapper) instead of a border per section
- Service page identity comes from the hero (image, eyebrow, overlay), not from colour

## Tokens

Defined in `src/app/globals.css` with `@theme inline`. Read the file for values. Never use a raw hex in a component.

| Token                        | Use                                                                                   |
| ---------------------------- | ------------------------------------------------------------------------------------- |
| `background`                 | Page base                                                                             |
| `surface`                    | Cards, nav, raised panels                                                             |
| `foreground`                 | Primary text                                                                          |
| `muted`                      | Secondary and caption text                                                            |
| `border`                     | Dividers, card outlines                                                               |
| `accent`                     | CTAs, links, highlights                                                               |
| `accent-hover`               | Hover and active (a separate token, because opacity on near-black turns orange brown) |
| `whatsapp`, `whatsapp-hover` | WhatsApp brand green, a deliberate exception                                          |

Utilities generated from them include `bg-surface`, `text-foreground`, `text-muted`, `border-border`, `bg-accent`, `hover:bg-accent-hover`.

The accent hex is provisional until Syd supplies the final logo (the current `public/images/logo.jpg` is a placeholder). Changing it is a one-line token edit.

## Z-index scale

`z-20` ScrollProgress bar (T5.10), `z-30` Navbar, `z-40` WhatsAppWidget, `z-50` MobileMenu overlay. The MobileMenu panel and the Services dropdown sit inside the sticky Navbar, so their real level is the Navbar's `z-30` and the bar must be below it (`z-20`), or it would paint over an open menu. Stay inside this scale for fixed and sticky layers. In-flow content may use `z-10` to sit above a sibling background (`HeroSection`, `ServiceHero`) or above a positioned sibling (the reviews carousel arrows over the `relative` track), and the decorative glow in `SectionHeading` and the wedge in `WhyChooseUsCard` (inside an `isolate` card, so it stays above the card background) use `-z-10`.

## Layout building blocks

- `SectionWrapper`: max-width and padding container, polymorphic (`as="section"` or `"div"`)
- `PageHero`: flat text banner for simple pages
- `HeroSection`: full-bleed homepage hero. Fixed height so the services grid stays visible
- `ServiceHero`: themed, image-backed hero for service pages. Do not extend `PageHero` for this
- `layout/ShopLabel` (T6.4): the "Shop" status after About in the desktop nav and the mobile menu. Plain text, never a link or button: no role, no `tabindex`, `cursor-default`, no `press`, no `underline-draw`, no hover. Muted token text (never `opacity-*`) with an outlined "Coming soon" pill in the shape of the dropdown's "Popular" tag, but muted, because accent would look clickable. The pill is `aria-hidden` and a `sr-only` " (coming soon)" follows the label, so a screen reader reads "Shop (coming soon)" once. Copy is `SHOP_LABEL`, `SHOP_TAG` and `SHOP_TAG_SR` in `constants.ts`. At 1024px the nav ends 32px before the call button, so it fits with no `min-w`. When the shop ships (Phase 8) the label becomes a link and drops the pill

## Motion

CSS first, no new Client Components. Phase 5 (T5.1 to T5.12, briefs in `docs/tickets/`) builds it. Tokens live in `globals.css` (`:root`), reusable blocks in `motion.css` as Tailwind `@utility` classes, so an effect is one class on an existing element. Do not add ad hoc animation outside a ticket. `PageTransition` (T3.31) is a 150ms opacity-only fade on route mount that starts at `--page-enter-from` (0.6), since T5.5.

**Intensity by page, phone first.** Homepage lively, service pages medium, About and 404 calm. Design the phone first, then add desktop-only extras.

**Rules**

- Animate only `opacity`, `translate`, `scale` and `rotate`. Never size, position, `flex`, padding or font size. Use the individual properties so they compose with `-skew-*`. One named exception: `details-expand` animates the `block-size` of `::details-content`. It only starts from a click or key press, so it adds no CLS (shifts within 500ms of input are excluded), it runs in Chromium only behind `@supports`, and it is the only way to animate a native `details`. Find-in-page opening an item is not input, so it counts as a small shift in Chromium. Accepted
- Every effect is progressive enhancement. Wrap it so reduced-motion visitors and browsers without support see the finished page, never a hidden one. Scroll effects: `@media (prefers-reduced-motion: no-preference)` plus `@supports (animation-timeline: view())`. Timed effects: the media query only. Tailwind classes use `motion-safe:`
- Scroll reveals use `animation-timeline: view()`, set after the `animation` shorthand, with `fill-mode: backwards` only (a held transform would block hover and trap `position: fixed`). One named exception: `scroll-progress` (T5.10) fills `forwards`, because a fixed bar with no children and no hover is trapped by nothing, and an iOS bounce past the bottom must not blank it. `animation-delay` does nothing on a scroll timeline: stagger by shifting `animation-range`. The range is `cover 0% cover var(--reveal-end)`, measured against the window, not the element (an `entry` range is measured against the element's own height, so a 4px stripe would pop). One named carve-out: the Footer's columns use an `entry` range (`reveal-stagger-entry`, T5.11), because the footer always ends at the window bottom and a `cover` range cannot finish there. It is safe only for columns of about 120px or more
- Reveal a wrapper, hover or press the element inside it. Never reveal something inside an `overflow-hidden` ancestor (it becomes the scroller and the effect never runs): use `overflow-clip`. Proven in T5.3: with `hidden`, every reveal inside `SectionShell` and `EnquiryBand` was captured, with `clip` none, and the page looks identical
- Reveal compact things (headings, cards), not tall containers: the range is a share of the window, so a tall element stays part-faded while most of it is on screen. Do not put a reveal on an element that has its own `translate-*`, `scale-*` or hover lift: wrap it. Reveal `block` elements, because individual `translate` and `scale` skip inline boxes
- Side slides (`reveal-left`, `reveal-right`) need an `overflow-clip` ancestor. A full-width card sliding in from the right pushes the page 8px wider at 375 while it moves. `SectionShell` is one, and so is Find Us (`overflow-x-clip` on its `SectionWrapper`, T5.9). `RelatedServices` and the other home sections are not. The end-of-scroll guards cannot see it
- The section glow stays static (T5.3 decision, kept in T5.10 and T5.11). The 404 stripe uses `STRIPE_STYLES` directly, so it does not draw
- Hover effects only under the hover media query. Tailwind's `hover:` variant already is, but the custom blocks in `motion.css` are not wrapped for you: each writes `@media (hover: hover)` itself (T5.4), or a tap leaves the effect stuck on a phone. Phones get `press` instead. Colour changes use `motion-safe:transition-colors`, except on an element that has `press`
- `press` owns the transition of any element it is on (T5.4). It lists the properties (colours, `translate`, `scale`) and gives each a duration slot (`--lift-duration`, `--press-duration`, each falling back to `--motion-fast`), so two blocks on one element cannot fight over `transition-property`. So an element with `press` carries no `transition-colors` or `transition-transform` of its own. A block that needs another transitioned property on that element adds it to both lists in `press`. Pseudo-element blocks (`sheen`, `underline-draw`) transition their own `::after` and never collide
- A `:active` rule inside a block must beat a `hover:scale-*` utility, so `press` is written `:active:not(:disabled)` (three selectors, above the two of a hover utility). Specificity decides it, not file order
- Never fade the hero image or the LCP text in from zero, and keep the page fade (`PageTransition`) above zero too: an invisible LCP element is not counted until it shows, and a 200ms fade from 0 cost about 180ms of LCP (T5.1 baseline). LCP text may rise (`hero-solid`). A decorative element that fades from 0 also keeps a tiny font-swap shift out of the CLS score (the 404 numeral). No parallax, count-up, cursor effects or `backdrop-filter` on the header (it traps the fixed mobile menu)
- Support (MDN, Nov 2026): `view()` timelines in Chrome 115, Safari and iOS 26, Firefox 159 (not stable yet). Older iOS and Firefox simply see no scroll effect. `::details-content` Chrome 131, Safari 18.4, Firefox 143. Height animation of `details` (`interpolate-size`) is Chrome only

**Tokens** (`:root` in `globals.css`): `--motion-fast` 150ms, `--motion-base` 300ms, `--motion-slow` 700ms, `--ease-settle`, `--ease-standard`, `--reveal-y` 1rem, `--reveal-x` 1.5rem, `--reveal-end` 30% (share of its pass up the window a reveal covers), `--stagger` 3% (extra range per neighbour, 8% was too much under `cover`), and from T5.4 `--press-scale` 0.97, `--lift-y` 0.25rem, `--sheen` (a `color-mix` of `foreground`, so no raw hex), `--pulse-delay` 2s, `--pulse-duration` 1s (one pulse, it runs twice) and `--pulse-reach` 1.5 (the ring grows to 1.5 times its size), and from T5.5 `--hero-zoom` 1.14 (where the hero image starts), `--hero-settle-duration` 1800ms, `--hero-duration` 900ms (one text step or stripe), `--hero-rise-y` 2rem (twice a scroll reveal, so the hero reads as an entrance), `--hero-step` 200ms (gap between hero text steps) and `--page-enter-from` 0.6, and from T5.8 `--depth-scale` 0.9 (how small a side review card is), `--depth-dim` 0.45 (the colour laid over it), `--depth-tilt` 8deg and `--depth-perspective` 1200px (lg and up only) and `--star-rest` 0.6 (stars on a side card), and from T5.10 `--pop-scale` 0.5 (where a badge starts: a step badge, and since T5.11 the coming-soon chip), and from T5.11 `--entry-reveal-end` 60% (how much of its entry a footer column covers), `--entry-stagger` 8% (extra entry per footer column, and `--entry-reveal-end` plus 5 times `--entry-stagger` must stay at 100% or less), `--pop-rotate` -6deg and `--pop-delay` 600ms (where the chip starts turned, and its wait after load). The build writes `150ms` as `.15s`, so a test reads a time token with its unit (`durationToken`). `html` also has `scroll-padding-top: calc(4rem + 1px)`, the sticky Navbar's height, so anchor jumps clear it.

**Blocks** (a block is listed as built once its ticket lands). Built: `details-expand` (T5.2, put on a `<details>`: the answer fades up 8px on open everywhere, and Chromium also grows and shrinks the height; Safari and Firefox close instantly; pad the answer, not `::details-content`); `reveal` (T5.3, fade and rise by `--reveal-y`), `reveal-left` and `reveal-right` (slide in from that side by `--reveal-x`, so `reveal-left` enters from the left), `reveal-stagger` (put on a parent: it reveals its direct children itself, so they carry no class, and each starts `--stagger` later than the one before, up to the 6th), `stripe-draw` (the skewed stripe's scale 0 to 1 on X, from its `origin-*`; `SectionHeading` sets the side the text starts on). Used by `SectionHeading` (number and h2 `reveal`, stripe `stripe-draw`), `ServicesGrid` (T5.5) and Why Choose Us (T5.6). Also built in T5.4, all CSS, all in `motion.css`:

- `press`: tap feedback. `touch-action: manipulation` always, and with no reduced-motion preference a press shrinks to `--press-scale` instantly and eases back over `--motion-fast` (a quick tap still shows). On every `LinkButton`, `ServiceCard`, the menu toggle, the footer social icons and the WhatsApp widget. It owns the element's transition (rule above). Reduced motion keeps the native tap highlight as the only feedback
- `lift`: a hovered card rises by `--lift-y` over `--motion-base`, hover devices only. It only sets the target, so the element needs a transition for `translate`: a clickable card gets it from `press`, a card that is not a link adds `motion-safe:transition-transform` (T5.6, Why Choose Us). `ServiceCard` uses it with `press`, and its icon tilts and grows a little (`group-hover`). No shadow animation. `ServiceCard` also gained the `LinkButton` keyboard focus ring, which closes the T3.10 follow-up
- `sheen`: one light sweep across a `LinkButton` primary on hover (`::after`, `--sheen`, `--motion-slow`, linear), hover devices only. The block sets `relative` and `overflow: clip`, and does not clip the focus ring (the ring is the button's own shadow). It reaches the calm pages (About, 404, Find Us) because `LinkButton` is shared. A secondary or ghost button has none
- `underline-draw`: an accent line draws in from the left under the Navbar links, the Services button and the dropdown row titles, on hover and keyboard focus. Its width is `--underline` (0 or 1), so a parent can hold it open (the Services button stays underlined while its dropdown is open, through `group-hover` and `group-focus-within`; a row sets it for its title through a named group). Do not nest one inside another, the variable inherits. Reduced motion: it appears at once, with no draw
- `pulse-ring`: a ring grows from the WhatsApp widget and fades, `--pulse-delay` after load, twice (1s each), then it stays still. A `::before` that copies the element's background and radius, resting at opacity 0 with no animation fill, so nothing can be left showing. Linear, because `--ease-settle` faded it in the first third of each cycle. The widget lives in the root layout, so it pulses once per full page load and not on client-side navigation

Built in T5.5, all timed CSS in `motion.css` (only the reduced-motion guard, each plays once at load and lets go: no fill, `backwards` covers the delay only):

- `hero-settle`: on the hero `<Image>` (and, since T5.10, on the service hero's category motif layer, not its photo). `scale` eases from `--hero-zoom` to 1 over `--hero-settle-duration`. The hero's `overflow-hidden` clips it (no scroll timeline, so that is safe here). Opacity is never touched
- `hero-in-N` (N = 1, 2, 3...): the element fades and rises by `--hero-rise-y` over `--hero-duration`, starting `(N - 1) * --hero-step` in. One element on its own is `hero-in-1`. It sets `--hero-delay` so `sheen-once` can wait for it. The homepage uses 1 to 3, the service hero 1 to 4 (T5.10)
- `hero-solid`: add to a `hero-in-N` element to drop the fade (it sets `--hero-fade-from: 1`). For LCP text, the homepage h1. A variable that inherits, so do not nest a `hero-in-N` inside one
- `hero-draw-N`: the skewed stripe draws out from its centre at step N (reuses `stripe-grow`). The homepage hero stripe is step 2, with the subtitle
- `sheen-once`: one sweep of the `sheen` band when the page loads, after the element's own `hero-in-N` has landed. Needs `sheen` on the same element (every primary `LinkButton` has it). It runs wherever the button shows, hover or not (the hero call button is below `lg` only)

The 404 numeral is `hero-in-1`. `ServicesGrid`: the h2 `reveal`s, the grid is `reveal-stagger` and each card sits in a wrapper `<div className="grid">` (the reveal sits on the wrapper, `lift` and `press` stay on the card, and the one-cell grid stretches the card so rows stay equal height).

Reviews carousel (T5.7), a native scroller with no new block. The track is `overflow-x-auto snap-x snap-mandatory` with `scrollbar-none`, `overscroll-x-contain` and `overflow-y-hidden` (`overflow-x: auto` turns a `visible` y into `auto`, which would make the track scroll vertically too). Its vertical `py` leaves room for the focus outline (T5.8's scale and tilt stay inside each slide's box, so they need none). The root sets `--slide` (85%, `md` 60%, `lg` a fixed 56rem, the T5.1 desktop card of 896px, because 60% of a 1024px track is far smaller) and `--gap` (12, 16, 24px). Slides are `w-(--slide) snap-center`, and `before:` and `after:` spacers `(100% - --slide) / 2 - --gap` wide let the first and last card centre at scroll 0 and at the end, so nothing scrolls on mount (CLS 0). `ReviewsSection` bleeds the track into the `SectionWrapper` padding (`-mx-4 sm:-mx-6 lg:-mx-8` plus `self-stretch`, because a `w-full` box in an `items-center` column does not grow with negative margins). A neighbour then shows 16px (375), 138px (768), 40px (1024) and 104px (1280 and up), and the 48px edge arrows sit 8px clear of the card at 1024. One set of arrows: a five-column grid puts them in row 2 beside the dots on phones and in row 1 over the track edges from `lg`, centred on the track (`z-10`, because the track is `relative`). Dots are a 32x44 tap target (40x48 from `lg`) and the visible dot is its `::before`: inactive `muted` (the `border` colour was 1.4:1 on the background), active accent and `scale-125`, so size as well as colour marks it, and T5.8 can stretch the same pseudo-element. `currentIndex` stays state, set by the controls and derived from the scroll on an animation frame (the slide whose middle is nearest the track's middle, from `offsetLeft`, which ignores transforms). A button or key scroll sets a target lock, so a long smooth scroll does not flick the index through every card. It is released when the scroll arrives, on pointer down or on a sideways wheel. Every route wraps (see the next paragraph). Left, Right, Home and End work on the focused track (ignored with Alt, Ctrl, Meta or Shift, and `preventDefault` stops the browser's own snap step from doubling the move, which shows with reduced motion). `scrollTo` is `'auto'` under reduced motion (nothing sets `scroll-behavior`, so it is instant). A neighbouring card is clickable (`aria-hidden:cursor-pointer`) but takes no `press`: the card gliding to the centre is the feedback (T5.8 scales the card inside it on a scroll timeline, which a press scale would sit on top of). This is a named exception to "every clickable element takes `press`" (the arrows and dots do). The track is a scroll container, so a timeline inside it binds to the track, not the page (T5.8 uses a named inline one per slide, below). No mouse drag, by decision. Autoplay is described below.

Reviews carousel wrap-around and hover tint (T5.7). Every route wraps, swipe included, by turning a window of slides, with no clones. After hydration (a `useSyncExternalStore` flag, so the server and no-JS markup stay in plain order) each slide gets an inline CSS `order` so the `anchor` slide sits in the middle slot (`floor(count / 2)`) and always has a real card on both sides. The spacers take `order-first` and `order-last`. The DOM order, and so the reading order, never changes. Fewer than three slides are not reordered. When a scroll settles on another slide, the window turns around it and `scrollLeft` is set outright to `scrollBefore + (the slide's new offsetLeft - its old one)`, in the same task, so the view does not move. Settling is `scrollend` where the browser has it, with a 150ms debounce after the last scroll event as the fallback, and never while a finger is down or a button scroll is still heading for its slide. A press (arrow, dot, key, neighbour click) turns the window around the slide in view first, so it never travels more than half a window, even when presses come before a scroll ended. So a wrap from the last card to the first is one card's glide, not a sweep across all five. Three gotchas, each found in a browser and each with a test: (1) set `scrollLeft` outright, never `+=`: after a layout change the browser re-snaps to the slide it was snapped to, and a `scrollLeft` read after that already includes it, so adding the offset moved the view one card too far in Chromium and WebKit; (2) Chromium fires `scrollend` before the animation frame that releases the target lock, so the settle must not clear its debounce timer until it is allowed to run; (3) React replays a click made during hydration before the render that applies `order`, so a press that arrives then is parked in `pendingRef` and carried out by the layout effect that applies the window (and it is the first hydration render that centres the first slide, which is not scroll position 0). Neighbouring cards tint on hover: an `::after` overlay (`rounded-lg` like `ReviewCard`, `aria-hidden:hover:after:bg-foreground/8`, `motion-safe:transition-colors`, hover devices only), a colour and never `opacity-*` so the faded guard stays quiet. The centre card has none. The window turn does not change a slide's position in a per-slide timeline (it is position based and the view does not move). Proven in T5.8 by sampling every frame across a turn in Chromium and WebKit: no card changed scale or dim.

Reviews carousel autoplay (T5.7, added after review at Haider's request, which reverses the Stage 1 "no autoplay" decision). The carousel moves on by itself, one slide every `AUTOPLAY_INTERVAL_MS` (3s: it is a glance on a homepage, not a read), through the same `goTo(currentIndex + 1)`, so it rides on the wrap window (card 5 to card 1 is a one-card glide) and each glide drives T5.8's per-slide timelines like any other scroll. The logic is `useReviewsAutoplay`, a hook beside the component. It runs only while at least half of the carousel is on screen (`IntersectionObserver`), and the page is visible. A mouse over it does not hold it: scrolling to the carousel leaves the cursor over it, so a hold on hover meant autoplay never started for a mouse (Haider found it, and tests on a fake clock had moved the mouse away first). It is one `setTimeout`, set by an effect keyed on `anchor`, which changes only once a scroll has settled, so a tick never fires mid-glide and each interval is counted from the move landing (a missed settle stops autoplay, which fails safe). Any use of the carousel ends it until the visitor presses play: an arrow, dot, key or neighbour click, a mouse press or sideways wheel on the track, the track scrolling under a finger, or focus anywhere in the carousel except the pause button. A finger merely landing on the track is NOT use (a `touch` `pointerdown`): the carousel fills much of a phone's screen, so a thumb scrolling the page lands on it, and stopping then meant autoplay was already paused when a phone visitor reached it (found in T5.8 review). The scroll handler stops it instead when the track moves while a finger is down (`touchingRef`), and a tap still stops it through focus or the click. The pause button (WCAG 2.2.2) is last in the page order, so the first tab stop is still the track (a screen-reader user reaches it after the content, which is acceptable because focus in the carousel stops autoplay anyway). It has a row of its own on a phone (`col-span-full row-start-3`, because 44px more does not fit beside the dots at 320px) and sits beside the dots from `sm`, with `ARROW_STYLES` and `press`. The root carries `data-autoplay="running|held"` so a test waits for a state and not for a number of frames. `aria-live` is `off` while autoplay is the visitor's choice and `polite` otherwise. Reduced motion (followed live), the server and a single review get no autoplay and no button; the server reads as reduced motion and a hidden page through `useSyncExternalStore`, so nothing starts before hydration. No new block and no dependency.

Reviews carousel depth (T5.8), two blocks in `motion.css`, no JavaScript, all inside the reduced-motion and `@supports (animation-timeline: view())` guards (without them every card looks the same, no ring):

- `carousel-depth` (on a slide): the slide declares `view-timeline: --slide-pass inline`, its own pass across the track (50% is centred). The name must NOT contain "view": `revealAudit` finds page reveals by that word and would count every card and star as a broken one. The card inside, and the slide's `::after` hover tint, run `depth-card` on that timeline: scale `--depth-scale`, shifted by half the lost width towards the centre (so the inner edge, and the phone's 16px peek, stay put), and from `lg` turned about the Y axis (`rotate: y`, negative on the right, so each face turns to the centre). The slide ITSELF is never transformed, because Playwright aims clicks by the transformed box, snapping uses the transformed box and the tint has to stay lined up. Perspective (`lg` up) is on the slide, because it only reaches direct children, not the track's grandchildren. The ring is the card's `::before` (2px accent, opacity 0 to 1: `border-color` may not animate) and the dim is the card's `::after` (a `background`-colour overlay, opacity `--depth-dim` to 0). It is an overlay and not `opacity`, which the faded guard would flag on every neighbour for ever. Order matters: a transformed child paints above an earlier `::before`, so the dim is `::after` to sit over the stars
- Keyframes hold the side look from 0% to 12% and 88% to 100% and the centre look from 48% to 52%, on the full cover range with fill `backwards` only. A neighbour rests at 2.3% (375), 11.2% (768, the tightest), 2.1% (1024) and 5.1% (1280) of its pass (or the mirror), so all sit on a flat stretch. Past the end of the range a slide is off screen, so there is no visible after-phase. If `--slide` or `--gap` change, check the 768px neighbour is still under 12%
